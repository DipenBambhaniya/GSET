1. System Software

System software sits between hardware and applications, translating and preparing programs to run.

Key ideas

  • Machine, assembly & high-level languages: increasing levels of abstraction above raw binary instructions.
  • Compilers vs interpreters: a compiler translates the whole program into machine code before execution; an interpreter executes source statements directly, one at a time (generally slower, but allows immediate execution/feedback).
  • Loading, linking & relocation: the linker combines object modules and resolves external references into one executable; the loader brings it into memory; relocation adjusts addresses to wherever it's actually loaded.
  • Macros: a named text-substitution shorthand expanded before/during assembly or compilation.
  • Debuggers: tools that let a programmer step through, inspect, and control a running program to find bugs.

2. Basics of Operating Systems

The operating system manages hardware resources and provides a consistent interface for applications to use them.

Key ideas

  • OS structure: monolithic (all services in one kernel), layered, microkernel (minimal kernel + services as user-level processes), and modular designs trade off performance vs. maintainability/reliability.
  • Operations & services: process/memory/file management, I/O, security, and a user interface (CLI/GUI) are core services an OS provides.
  • System calls: the controlled interface through which a user program requests kernel services (e.g. open(), fork(), read()), typically via a trap into kernel mode.
  • OS design & implementation: balances mechanism (how to do something) vs. policy (what to do), commonly written in a systems language like C.
  • System boot: firmware/bootloader loads the OS kernel into memory and transfers control to it when the machine powers on.

3. Process Management

A process is a program in execution; process management covers how the OS schedules, communicates between, and synchronizes many such processes safely.

Key ideas

  • Process scheduling & operations: the OS creates, schedules, and terminates processes, switching the CPU among them via a scheduler and dispatcher.
  • Interprocess communication (IPC): shared memory or message passing let independent processes exchange data; client–server systems often use sockets or RPC.
  • Process synchronization & the critical-section problem: when processes share data, access to the shared ("critical") section must guarantee mutual exclusion, progress, and bounded waiting.
  • Peterson's solution: a classic software-only two-process mutual-exclusion algorithm using a turn variable plus per-process "interested" flags.
  • Semaphores: an integer variable manipulated only via atomic wait()/signal() (P/V) operations — binary semaphores give mutual exclusion, counting semaphores manage a pool of resources.

4. Threads

Threads split a process into multiple independent flows of execution that share the same address space, enabling finer-grained concurrency.

Key ideas

  • Multicore programming: exploiting several CPU cores requires identifying tasks that can genuinely run in parallel.
  • Multithreading models: many-to-one (many user threads → one kernel thread), one-to-one (each user thread maps to its own kernel thread), and many-to-many (a pool of kernel threads shared by many user threads).
  • Thread libraries (e.g. POSIX Pthreads, Windows threads, Java threads) provide APIs to create and manage threads.
  • Implicit threading: frameworks (thread pools, OpenMP, task-based parallelism) create/manage threads for the programmer rather than manual thread creation.
  • Threading issues: fork/exec semantics with threads, thread cancellation, signal handling, and thread-local storage all need special care in multithreaded programs.

5. CPU Scheduling

When several processes are ready to run, the CPU scheduler decides which one runs next and for how long.

Key ideas

  • Scheduling criteria: CPU utilization, throughput, turnaround time, waiting time, and response time — different algorithms optimize different criteria.
  • Algorithms: FCFS (simple, can cause convoy effect), SJF (minimizes average waiting time but needs burst-time estimates), Priority scheduling (can starve low-priority jobs), and Round Robin (fair, time-sliced, good response time).
  • Thread scheduling: the OS may schedule kernel threads directly, while user-level threads are scheduled onto them by a thread library.
  • Multiple-processor scheduling: adds load balancing and processor affinity concerns across several CPUs/cores.
  • Real-time CPU scheduling: must guarantee tasks meet deadlines (hard or soft real-time), not just minimize average-case metrics.

6. Deadlocks

A deadlock is a state where a set of processes are each waiting for a resource held by another in the set, so none can proceed.

Key ideas

  • Deadlock characterization: all four conditions must hold simultaneously — mutual exclusion, hold-and-wait, no preemption, and circular wait.
  • Methods for handling deadlocks: prevent, avoid, detect-and-recover, or simply ignore the problem (the "ostrich algorithm," used by many general-purpose OSes).
  • Prevention denies at least one of the four necessary conditions structurally (e.g. requesting all resources at once).
  • Avoidance (e.g. Banker's algorithm) grants a request only if the resulting state is still "safe" — some ordering exists letting all processes finish.
  • Detection periodically checks for a cycle in the resource-allocation graph; recovery then terminates process(es) or preempts resources to break the cycle.

7. Memory Management

Memory management decides how processes are placed in and share physical memory, and how to cope with programs larger than available RAM.

Key ideas

  • Contiguous allocation & swapping: early schemes gave each process one contiguous memory block; swapping moves whole processes between memory and disk to free space.
  • Paging: divides memory into fixed-size frames/pages so a process's pages need not be contiguous — eliminates external fragmentation.
  • Segmentation: divides a program into variable-sized logical units (code, data, stack) that mirror its own structure.
  • Demand paging: pages are loaded from disk only when actually referenced, triggered by a page fault.
  • Page replacement: when memory is full, algorithms like FIFO, Optimal, and LRU choose which page to evict.
  • Allocation of frames & thrashing: too few frames per process causes excessive page faulting (thrashing), where the system spends more time paging than executing.
  • Memory-mapped files: map a file directly into a process's address space, letting file I/O be done via normal memory reads/writes.

8. Storage Management

Beyond RAM, the OS manages persistent mass storage — disks and their organization for reliability and performance.

Key ideas

  • Mass-storage & disk structure: disks are addressed as arrays of logical blocks, mapped onto physical sectors/tracks/cylinders.
  • Disk scheduling: algorithms like FCFS, SSTF, SCAN, and C-SCAN order pending disk requests to reduce total seek time.
  • Disk management: includes formatting, boot-block placement, and bad-block handling.
  • RAID structure: combines multiple disks for redundancy (mirroring) and/or performance (striping), at different RAID levels trading cost, speed, and fault tolerance.

9. File and Input/Output Systems

The file system organizes persistent data into named, structured units, while the I/O subsystem manages the diverse hardware devices beneath it.

Key ideas

  • Access methods & directory structure: sequential vs. direct (random) file access; directories organize files hierarchically (tree-structured, acyclic-graph).
  • File-system mounting & sharing: mounting attaches a file system to the directory tree at a mount point; sharing lets multiple users/systems access the same files, raising consistency concerns.
  • File-system implementation: on-disk and in-memory structures (superblock, inodes/FCBs) track files and free space.
  • Allocation methods: contiguous, linked, and indexed allocation each trade off fragmentation, access speed, and ease of growth.
  • Free-space management: bitmaps, linked lists, or grouping/counting techniques track which blocks are unused.
  • I/O hardware & kernel I/O subsystem: device controllers and drivers abstract hardware details; the kernel provides shared services — buffering, caching, spooling, and scheduling — common across many devices.
  • Application I/O interface: a uniform API (e.g. character/block device interfaces) lets applications use diverse devices through the same calls, which the kernel then transforms into actual hardware operations.

10. Security

OS security controls who can do what to which resources, and defends the system against malicious code and attackers.

Key ideas

  • Protection: mechanisms enforcing policies about resource access (distinct from security, which is about defending against threats).
  • Access matrix & access control: models which subjects (users/processes) hold which rights (read/write/execute) over which objects — implemented via access-control lists or capability lists.
  • Revocation of access rights: mechanisms to promptly remove previously granted permissions.
  • Program threats: viruses, worms, Trojan horses, and logic bombs hide or spread malicious behavior inside otherwise-normal-looking code.
  • System & network threats: denial-of-service, port scanning, and man-in-the-middle attacks target availability and communication integrity.
  • Cryptography as a security tool: encryption (symmetric/asymmetric) and hashing protect confidentiality and integrity; digital signatures support authentication and non-repudiation.
  • User authentication: passwords, biometrics, and multi-factor methods verify identity before granting access.
  • Implementing security defenses: firewalls, intrusion detection, and the principle of least privilege reduce the system's attack surface.

11. Virtual Machines

Virtualization lets one physical machine appear as several independent machines, each running its own OS.

Key ideas

  • Virtualization: a hypervisor abstracts physical hardware so multiple isolated virtual machines can share it.
  • Types of virtual machines: Type 1 (bare-metal) hypervisors run directly on hardware; Type 2 (hosted) hypervisors run as an application atop a host OS.
  • Implementations: full virtualization emulates complete hardware; paravirtualization requires a modified guest OS aware it's virtualized, for better performance.

12. Linux Operating Systems

Linux is a widely studied concrete example of a modern, modular, monolithic-kernel OS.

Key ideas

  • Design principles & kernel modules: a monolithic kernel that can dynamically load/unload modules (drivers, filesystems) at run time without a reboot.
  • Process management & scheduling: Linux uses the Completely Fair Scheduler (CFS) for regular tasks, alongside real-time scheduling classes for time-critical tasks.
  • Memory management, file systems, I/O: demand paging with a buddy-system allocator, support for multiple file systems (ext4, etc.) via a common Virtual File System (VFS) layer.
  • Interprocess communication & network structure: pipes, signals, message queues, shared memory, and sockets support communication both locally and over a network.

13. Windows Operating Systems

The Windows NT family illustrates a different design philosophy, layering services above a small protected executive.

Key ideas

  • Design principles & system components: a hybrid design — a protected "executive" providing core services, with subsystems layered above for API compatibility.
  • Terminal services & fast user switching: allow multiple user sessions (local or remote) to run concurrently on one machine.
  • File system: NTFS provides journaling, permissions (ACLs), and large-volume support.
  • Networking: built-in support for domains, shared resources, and standard network protocols.

14. Distributed Systems

A distributed system spreads computation and storage across multiple networked computers that must still cooperate correctly.

Key ideas

  • Types of network-based OSes: network OSes let users explicitly access remote resources; true distributed OSes make the network largely transparent to users.
  • Network structure & communication protocols: LAN/WAN topologies and layered protocol stacks provide the underlying communication.
  • Robustness & design issues: distributed systems must tolerate partial failures (some nodes down) via replication and fault-tolerance, and handle transparency, scalability, and consistency trade-offs.
  • Distributed file systems (e.g. NFS): let files be accessed over the network as if they were local, hiding the physical location of data.
