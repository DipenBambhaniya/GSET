1. Software Process Models

A software process model is a simplified, structured way of organizing the activities needed to build software — from prescriptive, plan-driven models to lightweight, adaptive agile ones.

Key ideas

  • Generic process model: framework activities (communication, planning, modeling, construction, deployment) recur across the project, wrapped by umbrella activities like risk management and quality assurance; a task set and process patterns define reusable work steps and recurring solutions.
  • Prescriptive process models: the Waterfall model (sequential phases, best when requirements are stable), Incremental model, and Spiral model (risk-driven, cyclical) plan the process up front.
  • Component-based & aspect-oriented development: build systems from reusable components, or factor out cross-cutting concerns (logging, security) separately from core logic.
  • Formal methods: use mathematically rigorous specification and verification to eliminate certain classes of defects, at high cost.
  • Agile process models: value working software, customer collaboration, and responding to change over rigid up-front planning. XP emphasizes pair programming, test-first development, and continuous integration; Scrum organizes work into fixed-length sprints; Adaptive Software Development, DSDM, Feature-Driven Development, and Crystal are other agile families with different emphases.
  • Web engineering: applies systematic process discipline to the particular demands (rapid change, broad audience, content-heavy) of web-based systems.

2. Software Requirements

Requirements engineering discovers, analyzes, and documents exactly what a system must do before (and while) it's built.

Key ideas

  • Functional vs. non-functional requirements: functional requirements state what the system must do; non-functional requirements state quality attributes/constraints — performance, security, usability, reliability.
  • Eliciting requirements: interviews, questionnaires, observation, and workshops draw out stakeholders' real (often initially unstated) needs.
  • Developing use cases: describe the step-by-step interaction between an actor and the system needed to achieve a specific goal.
  • Requirements analysis & modelling: organizes and refines raw requirements into models (e.g. data flow, class, state diagrams) that reveal gaps and conflicts.
  • Requirements review: stakeholders and developers jointly check requirements for correctness, completeness, and feasibility before design begins.
  • SRS document: the Software Requirements Specification precisely and unambiguously records what the system must do, serving as a contract between customers and developers.

3. Software Design

Design translates requirements into a blueprint for construction — deciding a system's structure before writing its code.

Key ideas

  • Abstraction: hides unnecessary detail, letting a designer reason at the right level (e.g. "sort the list" vs. the sorting algorithm's internals).
  • Architecture & patterns: architecture defines a system's overall structure; design patterns are proven, reusable solutions to recurring design problems.
  • Separation of concerns & modularity: divide a system into distinct modules, each addressing one responsibility, making the whole easier to understand and change.
  • Information hiding: a module exposes only what other modules need, hiding its internal implementation behind an interface.
  • Functional independence — cohesion & coupling: cohesion measures how closely related a module's internal responsibilities are (higher is better); coupling measures how much modules depend on each other (lower is better).
  • Design levels: object-oriented design (classes/objects), data design (data structures), architectural design (overall structure), user interface design, and component-level design (each module's internals) each address a different level of detail.

4. Software Quality

Quality is measured against defined factors and actively managed throughout the project, not just checked at the end.

Key ideas

  • McCall's quality factors: grouped into product operation (e.g. correctness, reliability, usability), product revision (maintainability, flexibility, testability), and product transition (portability, reusability, interoperability).
  • ISO 9126 quality factors: a standardized model covering functionality, reliability, usability, efficiency, maintainability, and portability.
  • Quality control vs. quality assurance: QC finds defects in the product itself (e.g. testing, inspections); QA focuses on the process used to build the product, aiming to prevent defects in the first place.
  • Risk management: identifies, analyzes, prioritizes, and tracks project risks throughout development.
  • RMMM: Risk Mitigation, Monitoring, and Management — the plan for reducing risk probability/impact, watching for risk indicators, and responding if a risk materializes.
  • Software reliability: the probability that software will operate without failure for a specified period under specified conditions.

5. Estimation and Scheduling of Software Projects

Before committing to a delivery date, a project's size, cost, effort, and schedule must be estimated as accurately as possible.

Key ideas

  • Software sizing: estimating how big the software will be — commonly in LOC (lines of code) or Function Points (FP, based on delivered functionality — inputs, outputs, inquiries, files — independent of language).
  • Estimating cost and effort: derived from size estimates combined with productivity data and adjustment factors.
  • Estimation models — COCOMO: the Constructive Cost Model estimates effort/time from estimated size (KLOC) and project mode (organic, semi-detached, embedded) plus cost-driver attributes.
  • Project scheduling and staffing: breaks the project into tasks with dependencies and durations, then assigns people — often visualized with timeline (Gantt) charts.

6. Software Testing

Testing verifies that software has been built correctly and validates that it meets the user's real needs.

Key ideas

  • Verification vs. validation: verification asks "are we building the product right?" (conforms to spec); validation asks "are we building the right product?" (meets the user's actual needs).
  • Error, fault, bug, failure: a human error introduces a fault (defect) in the code, which may manifest as an observable failure at run time — "bug" is the informal term for a fault.
  • Unit & integration testing: unit testing checks individual components in isolation; integration testing checks that combined components work together correctly.
  • White-box vs. black-box testing: white-box testing uses knowledge of internal code/logic (e.g. basis path testing, control structure testing) to derive test cases; black-box testing derives test cases purely from the specified inputs/outputs, ignoring internal structure.
  • Alpha & beta testing: alpha testing happens at the developer's site with the developer present; beta testing happens at real customer sites without the developer present.
  • Regression, performance & stress testing: regression testing re-runs tests after changes to catch newly introduced breakage; performance testing measures responsiveness/throughput; stress testing pushes the system beyond normal load to find its breaking point.

7. Software Configuration Management

As software evolves over its lifetime, configuration management tracks and controls exactly what changed, when, and why.

Key ideas

  • Change control: a formal process for proposing, evaluating, approving, and tracking changes to a software baseline.
  • Version control: systems (e.g. Git) track the history of every file change, enabling collaboration, branching, and rollback to prior states.
  • Software reuse: building new systems (partly) from existing, proven components rather than from scratch.
  • Software re-engineering: restructuring or rewriting existing software to improve its quality/maintainability while preserving its overall function.
  • Reverse engineering: analyzing an existing system (often with little/no documentation) to recover its design or specification.
