1. Database System Concepts and Architecture

Before touching SQL, it helps to see how a DBMS is structured internally, and why that structure lets applications stay insulated from storage details.

In simple words: A database keeps the "how data looks to the user," "how data is logically organized," and "how data is actually stored on disk" as three separate layers, so changing one (say, adding an index) doesn't force every application to be rewritten. Think of it like a restaurant menu (what customers see) staying the same even if the kitchen changes how it stores ingredients.

Key ideas

  • Data models, schemas, instances: a data model gives the concepts to describe a database's structure; a schema is that structure's description (rarely changed); an instance is the actual data at a moment in time (changes constantly).
  • Three-schema architecture: separates external (per-user views), conceptual (community logical schema), and internal (physical storage) levels.
  • Data independence: logical independence shields external views from conceptual schema changes; physical independence shields the conceptual schema from storage/internal changes.
  • Database languages & interfaces: DDL (defines schema), DML (queries/manipulates data), DCL (controls access) — accessed via query interfaces, forms, APIs.
  • Centralized vs. client/server architecture: centralized systems run everything on one machine; client/server splits the user interface/application (client) from the database engine (server), often over a network.

2. Data Modeling

Data modeling is about deciding what the database's structure should be — first conceptually (ER diagrams), then formally (the relational model).

In simple words: Before building any tables, you sketch out the "things" your system cares about (students, courses), what facts you know about each one (a student's ID, name), and how they connect (a student enrolls in a course). That sketch is the ER diagram; the relational model then turns it into actual tables with rules that keep the data trustworthy.

Key ideas

  • Entity-Relationship (ER) diagrams: model real-world entities, their attributes, and the relationships between them — the standard first step in conceptual design.
  • Relational model & constraints: data is organized into relations (tables) of tuples (rows); key constraints (primary/candidate key), entity integrity, and referential integrity (foreign keys) keep data valid.
  • Relational database schemas & update operations: insert, delete, and update operations must respect constraints — violations must be rejected, cascaded, or handled by a defined policy.
  • Relational algebra: a procedural query language of operations (σ select, π project, ⋈ join, ∪ union, − difference, ×) on relations.
  • Relational calculus: a declarative alternative — specifying what data to retrieve (via predicate logic) rather than how to compute it.
  • Codd's rules: 12 rules (Codd, 1985) defining what a DBMS must support to be considered truly relational.

3. SQL

SQL is the standard language for defining, querying, and controlling data in a relational database.

In simple words: SQL is how you "talk" to a database: you use it to build the tables (DDL), put data in / change it / read it back (DML), and decide who is allowed to touch what (DCL). SQL injection is what happens when an app carelessly pastes a user's typed text straight into a query, letting someone type in extra commands the app never intended to run.

Key ideas

  • Data definition & data types: CREATE/ALTER/DROP TABLE define schema structure and column types (INT, VARCHAR, DATE, etc.).
  • Constraints: PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, CHECK enforce data validity declaratively.
  • Queries & DML: SELECT retrieves data; INSERT, UPDATE, DELETE add, modify, and remove rows.
  • Views: a virtual table defined by a stored SELECT query — it doesn't store data itself, just presents it.
  • Stored procedures & functions: precompiled, reusable blocks of SQL/procedural logic executed on the server.
  • Database triggers: procedures that fire automatically in response to specified events (INSERT/UPDATE/DELETE) on a table.
  • SQL injection: a security vulnerability where untrusted input is concatenated into a query, letting an attacker alter its logic — prevented with parameterized queries/prepared statements.

4. Normalization for Relational Databases

Normalization systematically restructures relations to remove redundancy and the update anomalies it causes, guided by functional dependencies.

In simple words: If the same fact (like a customer's address) is copied into many rows, an update can miss some copies and leave the data contradicting itself. Normalization splits tables apart, step by step (1NF, 2NF, 3NF...), so each fact is stored in exactly one place — at the cost of needing joins to bring related facts back together when you query.

Key ideas

  • Functional dependencies: X → Y means each value of X determines exactly one value of Y — the basis for detecting redundancy.
  • Normal forms: 1NF (atomic values), 2NF (no partial dependency on part of a composite key), 3NF/BCNF (no transitive dependency on non-key attributes) progressively remove anomalies.
  • Query processing & optimization: a query is parsed into an execution plan; the optimizer picks the cheapest plan using statistics, indexes, and join-order heuristics.
  • Transaction processing: a transaction is a unit of work satisfying the ACID properties — Atomicity, Consistency, Isolation, Durability.
  • Concurrency control: locking, timestamp ordering, and optimistic techniques prevent conflicting transactions from corrupting data when run simultaneously.
  • Database recovery: logs (write-ahead logging) and checkpoints let the system restore a consistent state after a crash.
  • Object / object-relational databases: extend the relational model with object-oriented features (classes, inheritance, complex types).
  • Database security & authorization: authentication, access-control privileges (GRANT/REVOKE), and roles restrict who can do what to which data.

5. Enhanced Data Models

Beyond the classic relational model, specialized data models address needs that plain tables handle awkwardly.

In simple words: Plain rows-and-columns tables aren't the best fit for everything — tracking how a value changed over time, storing a photo or video, handling map coordinates, or spreading data across many separate computers all need their own specialized kind of database, built as an extension or alternative to the relational model.

Key ideas

  • Temporal databases: track how data changes over time (valid time vs. transaction time), supporting "as of" and history queries.
  • Multimedia & deductive databases: multimedia databases store/query images, audio, and video; deductive databases add rule-based (logic-programming style) inference over stored facts.
  • XML and Internet databases: store and query semi-structured, self-describing XML data, common for web data exchange.
  • Mobile databases & GIS: mobile databases handle intermittent connectivity and location-awareness; Geographic Information Systems manage spatial data (maps, coordinates, regions).
  • Genome data management: specialized storage/querying for very large, sequence-oriented biological data.
  • Distributed databases & client-server architectures: data is stored across multiple sites but appears as one logical database, requiring distributed query processing and transaction coordination.

6. Data Warehousing and Data Mining

A data warehouse consolidates historical data for analysis, and data mining extracts patterns and predictive models from it.

In simple words: A regular database is built for quick day-to-day transactions (OLTP); a data warehouse instead stockpiles years of historical data so analysts can ask big-picture questions (OLAP) like "which products sell best each season?" Data mining then digs through that stockpile automatically to find patterns a human might never spot by eye.

Key ideas

  • Data modeling for warehouses: star and snowflake schemas organize measures (facts) around descriptive dimensions; concept hierarchies let users drill down/roll up (e.g. day → month → year).
  • OLAP vs OLTP: OLTP handles many small, fast transactional read/writes (e.g. order entry); OLAP runs complex, read-heavy analytical queries over large historical, multidimensional data.
  • Association rule mining: finds patterns like "customers who buy X also buy Y" (market-basket analysis).
  • Classification & regression: supervised techniques predicting a category (classification) or a continuous value (regression) from labeled training data.
  • Clustering: unsupervised grouping of similar data points without predefined labels.
  • Support Vector Machine, k-Nearest Neighbour, Hidden Markov Model: SVM finds a maximum-margin separating boundary between classes; k-NN classifies/predicts using the closest labeled examples; HMMs model sequences with hidden states (e.g. speech, POS tagging).
  • Summarization, dependency modeling, link/sequencing/social-network analysis: further mining tasks — condensing data, finding variable dependencies, analyzing graph/link structures, ordered sequences, and social network patterns.

7. Big Data Systems

Big Data systems store and process datasets too large, fast, or varied for a single traditional database server.

In simple words: When data is too big, too fast-arriving, or too messy in shape for one server to handle, the job gets split across many machines working together — Hadoop and MapReduce are the classic tools for that, spreading storage (HDFS) and computation (Map, then Reduce) across a whole cluster.

Key ideas

  • Big Data characteristics: commonly the "3 (or more) Vs" — Volume, Velocity, Variety (plus Veracity, Value).
  • Types of Big Data: structured (tables), semi-structured (JSON/XML/logs), and unstructured (text, images, video).
  • Big Data architecture: layers for ingestion, storage, processing, and serving/analytics, typically distributed across many machines.
  • MapReduce: a programming model splitting work into a parallel Map phase (produces key-value pairs) and a Reduce phase (aggregates values sharing a key).
  • Hadoop: an open-source framework implementing MapReduce over a distributed file system, scaling out across commodity hardware.
  • HDFS (Hadoop Distributed File System): splits large files into replicated blocks spread across many DataNodes, with a NameNode managing filesystem metadata and block locations.

8. NOSQL

NoSQL ("not only SQL") databases trade some relational guarantees for horizontal scalability and flexible schemas, suited to specific access patterns.

In simple words: Not every app needs strict tables with rigid columns and guaranteed instant consistency everywhere. NoSQL databases relax some of those relational guarantees in exchange for being easier to spread across many servers and more flexible about what shape each record can take — useful for huge, fast-growing, or unevenly-structured data.

Key ideas

  • NoSQL and query optimization: NoSQL stores generally favor horizontal scalability and availability, often relaxing strict consistency (favoring eventual consistency) per the CAP theorem's trade-offs.
  • Different NoSQL products: key-value (Redis, DynamoDB), document (MongoDB), column-family (Cassandra, HBase), and graph (Neo4j) databases, each suited to a different data shape.
  • Querying and managing NoSQL: query APIs are typically simpler than SQL and model-specific (e.g. document queries, graph traversals) rather than a single universal language.
  • Indexing and ordering data sets: secondary indexes and sorted key ranges support efficient lookups despite the lack of relational joins.
  • NoSQL in the cloud: many NoSQL databases are offered as managed cloud services, scaling storage/throughput elastically on demand.
