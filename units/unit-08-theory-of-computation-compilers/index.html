1. Theory of Computation

Before studying specific machine models, it helps to see what a "language" formally is, and that some problems are provably impossible for any algorithm to solve.

Key ideas

  • Formal language: a set of strings over a fixed alphabet, typically defined by a grammar or accepted by a machine model.
  • Non-computational (unsolvable) problems: some well-defined problems provably have no algorithm that solves them for all inputs.
  • Diagonal argument: a proof technique (from Cantor) that constructs an object differing from every item in an assumed complete list/enumeration — the core technique behind proving the Halting Problem undecidable.
  • Russell's Paradox: considering "the set of all sets that do not contain themselves" leads to a contradiction, exposing the danger of unrestricted self-reference — conceptually related to diagonalization arguments in computability.

2. Regular Language Models

Regular languages are the simplest class in the Chomsky hierarchy — recognizable with only a fixed, finite amount of memory.

Key ideas

  • DFA vs. NFA: a Deterministic Finite Automaton has exactly one transition per symbol per state; a Non-deterministic FA may have several (or none) — but both recognize exactly the same class of languages (regular languages), since every NFA has an equivalent DFA.
  • Regular expressions, grammars, and languages: regular expressions, regular grammars, and finite automata are three equivalent ways to define the same class of regular languages.
  • Properties of regular languages: closed under union, concatenation, Kleene star, intersection, and complement.
  • Pumping Lemma: a tool for proving a language is not regular, by showing any sufficiently long string in it can be "pumped" (a middle section repeated) to produce a string outside the language.
  • Lexical analysis: a compiler's first phase uses regular expressions/finite automata to recognize and classify tokens (keywords, identifiers, operators) in the source text.

3. Context Free Language

Context-free languages add a stack's worth of memory over regular languages, letting them express nested/recursive structure — exactly what programming language syntax needs.

Key ideas

  • Pushdown Automaton (PDA): a finite automaton extended with an unbounded stack, giving it enough memory to recognize context-free languages; PDAs and context-free grammars are equivalent in power.
  • Context-Free Grammar (CFG): productions of the form A → α (a single non-terminal produces a string of terminals/non-terminals) define a context-free language.
  • Chomsky Normal Form & Greibach Normal Form: standardized production forms (A → BC / A → a, and A → aα respectively) that simplify parsing and proofs while preserving the language.
  • Ambiguity: a grammar is ambiguous if some string has more than one distinct parse tree/leftmost derivation — problematic since it means the grammar doesn't uniquely determine meaning.
  • Properties of CFLs: closed under union, concatenation, and Kleene star, but not closed under intersection or complement in general.

4. Turing Machines (TM)

The Turing machine is the most powerful classical model of computation, believed to capture exactly what is "effectively computable."

Key ideas

  • Standard TM & variations: multi-tape, multi-track, and non-deterministic TMs are all provably equivalent in computing power to the standard single-tape TM.
  • Universal Turing Machine: a single TM that, given the description of any other TM plus its input, simulates that machine — the theoretical ancestor of the stored-program computer.
  • Church-Turing Thesis: any function computable by an intuitive "effective procedure"/algorithm can be computed by some Turing machine — a thesis (not a formal theorem), but foundational to computability theory.
  • Recursive & recursively-enumerable languages: a language is recursive if some TM always halts and correctly decides membership; it's recursively enumerable if some TM halts and accepts on every string in the language (but may loop forever on non-members).
  • Chomsky hierarchy: nests four language classes by grammar restriction — regular ⊂ context-free ⊂ context-sensitive ⊂ recursively enumerable (unrestricted grammars) — each requiring a more powerful machine to recognize.

5. Unsolvable Problems and Computational Complexity

Some problems are provably beyond any algorithm's reach, while others are merely impractically slow — these are two very different kinds of "hard."

Key ideas

  • Unsolvable (undecidable) problems: problems for which no algorithm can exist that correctly answers every instance.
  • The Halting Problem: deciding whether an arbitrary program halts on an arbitrary input — the canonical undecidable problem, proven via a diagonalization argument.
  • Post Correspondence Problem: given two lists of strings, decide if some sequence of indices makes both lists' concatenations equal — another classic undecidable problem, useful for proving other problems undecidable via reduction.
  • Unsolvable problems for CFLs: certain natural questions about context-free grammars (e.g. ambiguity, equivalence of two CFGs) are also undecidable.
  • Tractable vs. intractable: tractable problems are solvable in polynomial time; intractable problems require (as far as is known) super-polynomial time in the worst case — a different notion of "hard" than undecidability, since intractable problems are still solvable, just slowly.

6. Syntax Analysis

A compiler's parser checks that a token stream conforms to the language's grammar and builds a structural representation of it.

Key ideas

  • Associativity & precedence: grammar rules (or explicit precedence declarations) resolve how operators group in expressions like a + b * c.
  • Grammar transformations: eliminating left recursion and left-factoring reshape a grammar so top-down parsers can handle it.
  • Top-down parsing: builds the parse tree from the root down, predicting which production to expand next; recursive descent implements this directly as mutually recursive procedures; LL(1) parsing uses one token of lookahead and a parsing table to decide deterministically.
  • Bottom-up parsing: builds the parse tree from the leaves up via repeated shift/reduce steps; LR parsers (and the more memory-efficient LALR(1) variant) handle a broader class of grammars than LL parsers and are the basis of most parser-generator tools (e.g. yacc/bison).

7. Semantic Analysis

After parsing confirms a program is syntactically valid, semantic analysis checks that it actually makes sense (types, scopes) and computes meaning attached to the parse tree.

Key ideas

  • Attribute grammars & syntax-directed definitions: attach semantic rules/attributes to a grammar's productions, computing properties (e.g. a type, a value) as the tree is built or traversed.
  • Synthesized attributes: computed from a node's children (flow upward); inherited attributes: computed from a node's parent/siblings (flow downward or sideways).
  • Dependency graphs & evaluation order: attribute dependencies determine a valid order to evaluate them; S-attributed definitions use only synthesized attributes (evaluable bottom-up); L-attributed definitions also allow inherited attributes evaluable left-to-right in one pass.
  • Type-checking: verifies operations are applied to compatible operand types, catching type errors before code generation.

8. Run Time System

The run-time system manages memory and control flow while a compiled program actually executes, especially across function/procedure calls.

Key ideas

  • Storage organization: a running program's memory is typically divided into code, static data, a heap, and a stack.
  • Activation tree & activation record: the activation tree captures the call/return structure of a running program over time; each call creates an activation record (stack frame) holding local variables, parameters, and the return address.
  • Stack allocation: works well for languages where activation records can be discarded in strict LIFO order as calls return.
  • Parameter passing mechanisms: call-by-value, call-by-reference, and call-by-name/need each define how arguments connect to a callee's parameters.
  • Symbol table: a compiler-maintained structure recording each identifier's type, scope, and storage location, consulted throughout compilation.

9. Intermediate Code Generation

Rather than translating directly from source to machine code, most compilers first generate a machine-independent intermediate form.

Key ideas

  • Intermediate representations (e.g. three-address code, syntax trees) sit between source and target code, making the compiler more portable and modular — front-end analysis and back-end code generation can be developed independently.
  • Translating declarations: computes storage layout/offsets for variables based on their declared types.
  • Translating assignments & control flow: expressions and statements (if/while/for) are translated into sequences of intermediate instructions with explicit jumps/labels.
  • Boolean expressions: often compiled using "jumping code" — evaluating to a control-flow jump rather than a stored true/false value, and supporting short-circuit evaluation.
  • Procedure calls: translated into code that sets up parameters/activation records and transfers control, consistent with the chosen parameter-passing mechanism.

10. Code Generation and Code Optimization

The compiler's back end turns intermediate code into efficient target-machine instructions.

Key ideas

  • Control-flow & data-flow analysis: the control-flow graph models possible execution paths through basic blocks; data-flow analysis tracks facts (e.g. which definitions of a variable reach a point) across that graph to enable optimization.
  • Local optimization: improvements within a single basic block (e.g. constant folding, common subexpression elimination).
  • Global optimization: improvements that consider information flowing across multiple basic blocks/the whole function.
  • Loop optimization: techniques like moving loop-invariant code out of a loop, or strength reduction, cut down repeated work across iterations.
  • Peephole optimization: examines and improves a small, localized window ("peephole") of generated instructions — e.g. removing redundant loads/stores.
  • Instruction scheduling: reorders generated instructions to better exploit pipelining/hardware parallelism without changing the program's meaning.
